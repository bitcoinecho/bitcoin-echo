**Test 2: Corrupted size field — verify detection**

This tests `block_storage_read()` behavior when the on-disk block file has a corrupted size field. Approach:
1. Write a normal block to get a valid position
2. Directly open the blk*.dat file and overwrite the 4-byte size field at that position with a value > ECHO_MAX_BLOCK_SIZE (e.g., 0xFFFFFFFF)
3. Attempt `block_storage_read()` at that position
4. Verify it returns an error (ECHO_ERR_INVALID or similar), NOT a 4GB malloc attempt

If `block_storage_read()` does NOT currently validate size against ECHO_MAX_BLOCK_SIZE before malloc, note this as a finding and add bounds check validation to the test expectation. The test documents the expected behavior even if the current code needs a fix (which can be addressed in the same task — add the bounds check to `blocks.c` if missing).

**Test 3: Truncated read — file shorter than size field claims**

1. Write a normal block to get a valid position and file path
2. Truncate the blk*.dat file (via `ftruncate()` or by overwriting with a shorter file) so it's shorter than the size field claims
3. Attempt `block_storage_read()` at that position
4. Verify it returns ECHO_ERR_IO or equivalent, not garbage data or a crash

**Test 4: Near-4x witness weight limit**

Create a block near the theoretical SegWit weight limit (~4 MB witness data). This is close to `ECHO_MAX_BLOCK_SIZE` but tests the witness-specific boundary. If `ECHO_MAX_BLOCK_SIZE` is 4MB, test at `ECHO_MAX_BLOCK_SIZE - 1` to verify near-boundary handling. If there's a separate witness weight constant, use that.
