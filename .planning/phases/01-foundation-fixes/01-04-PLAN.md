<objective>
Ensure block storage writes are durable before the block index records the file position, eliminating GAP errors where chaser_confirm tries to read a block whose data has not been flushed to disk.

Purpose: Currently `block_storage_write()` is synchronous but `BLOCK_STORAGE_FLUSH_INTERVAL=100` means data may not be flushed for up to 99 blocks. The block index is updated immediately after write, so chaser_confirm can try to load a block from a position that points to unflushed data. The fix ensures the index is never ahead of durable data.

Output: Modified write/flush/index ordering that guarantees durability before indexing.
</objective>

**Step 2: Choose fix strategy**

Per research, two approaches exist. Choose based on what node_store_block() reveals:

**Strategy A (preferred — flush-before-index):**
After `block_storage_write()` returns the file position, call `block_storage_flush()` (or add fflush to the write file) BEFORE updating the block index with the position. This ensures the data the position points to is on disk before the index records it.

To avoid per-block fsync performance degradation, use a batch-aware flush:
- Track whether we're in a download batch context
- Flush at batch completion boundaries (when download_mgr batch remaining hits 0)
- OR: change `block_storage_write()` to fflush (not fsync) after each write — fflush to OS page cache is fast, fsync to physical media is slow. fflush is sufficient because the GAP error occurs when the FILE* buffer hasn't been written to the OS, not when the OS hasn't synced to disk.

**Strategy B (callback-based — only if Strategy A doesn't fit):**
Add a completion callback to `block_storage_write()`:
```c
typedef void (*block_write_complete_fn)(const block_file_pos_t *pos, void *ctx);
echo_result_t block_storage_write_async(block_file_manager_t *mgr,
                                         const uint8_t *data, size_t len,
                                         block_write_complete_fn on_complete,
                                         void *ctx);
```

**Step 3: Implement**

For Strategy A (most likely):

1. In `blocks.c`, ensure that after each `fwrite()` to the current write file, `fflush()` is called on the write file handle. This pushes data from the C stdio buffer to the OS page cache. This is NOT fsync — it's lightweight.

   Alternatively, if `BLOCK_STORAGE_FLUSH_INTERVAL` controls fflush frequency, change it to flush every write during the critical path, or remove the interval batching for writes (keep fsync batching if it exists separately).

2. In `node.c`, verify the ordering in `node_store_block()`:
   - `block_storage_write()` — writes data AND flushes to OS
   - `block_index_db_update_position()` — records file position
   - `download_mgr_block_received()` — notifies download manager

   If the current ordering is different, rearrange to match.

3. If `blocks.c` has separate fflush and fsync calls, ensure fflush happens per-write but fsync can remain batched (every N blocks) for performance.

**Performance constraint:** Per research Pitfall 5, adding fsync on every block write would kill IBD throughput (< 10 blocks/sec). fflush is acceptable (pushes to OS page cache, OS handles physical write asynchronously). Only add fsync at batch completion boundaries if at all.

**Comment requirement:** Add a clear comment at the flush site explaining: "Flush write buffer to OS before recording position in block index. Without this, chaser_confirm may read a position pointing to unflushed data (GAP error)."
