  <name>Task 1: Fix batch remaining count mismatch in download manager (BUGF-01)</name>
  <files>src/protocol/download_mgr.c</files>
  <action>
**Root cause (from research):** When a batch is cloned via `batch_node_clone()` (download_mgr.c:95-110), the clone copies the full `work_batch_t` including the `received[]` bitmap via memcpy. If the original has `received[i]=true` for blocks already received, the clone inherits those marks. But `remaining` in the clone was set from the original's current `remaining` — which was already decremented for those received blocks. So `remaining` is correct for the original's state but not for the clone's inherited bitmap.

When the clone's peer later receives those already-marked blocks, `block_received()` sees `received[i]=true` and correctly skips the decrement. But the damage is already done: `remaining` was copied from the original AFTER some decrements, and the bitmap was copied WITH those marks already set. The count is consistent if you think of it as "remaining for blocks NOT in received[]" — but the safety check at `peer_request_work()` (lines 596-611) counts unreceived entries in the bitmap and compares to `remaining`, finding a mismatch.

**Fix approach:**

1. Read `batch_node_clone()` carefully (lines ~95-110). After the memcpy of the full batch struct, recalculate `remaining` to match the actual state of the `received[]` bitmap:

```c
/* After cloning, recalculate remaining to match received[] bitmap.
 * The original's remaining was decremented as blocks arrived, but the
 * clone inherits the bitmap state. Remaining must equal the number of
 * false entries in received[]. */
size_t count = 0;
for (size_t i = 0; i < clone->batch.block_count; i++) {
    if (!clone->batch.received[i]) {
        count++;
    }
}
clone->batch.remaining = count;
```

2. Also verify in `download_mgr_block_received()` that the `received[i]` check happens BEFORE decrementing `remaining`. Read the function to confirm this guard exists. If it does, the clone fix above is sufficient. If not, add the guard:

```c
if (batch->received[index]) {
    /* Already received (duplicate from original batch holder) — skip */
    return;
}
batch->received[index] = true;
batch->remaining--;
```

3. Do NOT modify the safety check at lines 596-611 — it should become unreachable after this fix, but keep it as a defense-in-depth assertion. Change its log level from LOG_ERROR to LOG_WARN since it's now a "should never happen" assertion rather than a known bug path.

**Anti-pattern from research:** Do NOT reset the `received[]` bitmap on re-assignment. Do NOT reset `remaining` to `block_count`. The bitmap is the source of truth; `remaining` must be derived from it.
  </action>
  <verify>
Run `make` — compiles with zero warnings. Grep for the recalculation loop in `batch_node_clone` or equivalent clone function. Verify the safety check LOG_ERROR at lines ~596-611 is downgraded to LOG_WARN. Run `make test` — existing download manager tests pass.
  </verify>
  <done>
Batch clone recalculates `remaining` from actual `received[]` bitmap state. Block receipt guard prevents double-decrement. Safety check downgraded from LOG_ERROR to LOG_WARN (defense-in-depth). No remaining count mismatches during normal operation.
  </done>

<task type="auto">
  <name>Task 2: Fix duplicate peer address race in connection setup (BUGF-02)</name>
  <files>src/app/node.c, src/protocol/discovery.c</files>
  <action>
**Root cause (from research):** The duplicate check in `node.c:3271-3292` compares against peer state AFTER slot selection. `discovery_mark_address_in_use()` is called before the per-peer loop, but `discovery_select_outbound_address()` can return the same address in a subsequent iteration because the `in_use` flag check and the peer state check happen at different points. The event loop is single-threaded for connection setup, so this is a within-iteration logic error, not a true thread race.

**Fix approach:**

1. Read `discovery_select_outbound_address()` in `src/protocol/discovery.c` (lines ~470-543 per research). Verify it checks the `in_use` flag. If so, the issue is that `mark_address_in_use()` is called too late — after the address has already been selected but before the actual connection is established.

2. In `src/app/node.c`, at the connection setup loop (~line 3240-3300), ensure this ordering:
   a. `discovery_select_outbound_address()` returns candidate address
   b. Check candidate against ALL currently connected/connecting peers (the loop at line 3273)
   c. If duplicate found, skip this candidate (continue to next iteration)
   d. `discovery_mark_address_in_use()` — mark BEFORE calling `peer_connect()`
   e. `peer_connect()` — establish connection

   The key fix is ensuring step (b) happens BEFORE step (d) and (e), and that `mark_address_in_use` is called atomically with the duplicate check — no window between check and mark.

3. If the per-peer duplicate check at line 3273 uses a simple loop over peers comparing addresses, verify it compares the full address (IP + port), not just IP. Read the comparison logic.

4. Remove or downgrade the defensive LOG_WARN at line 3280 to LOG_DEBUG since the fix should prevent it from firing. Keep it as a debug assertion.

**Important:** The node event loop is single-threaded for connection setup. This is not a mutex issue — it's a logic ordering issue within the same thread's iteration.
  </action>

Run `make` — compiles with zero warnings. Grep `node.c` for the connection setup loop — verify `mark_address_in_use` is called after duplicate check but before `peer_connect`. Run `make test` — existing tests pass.
