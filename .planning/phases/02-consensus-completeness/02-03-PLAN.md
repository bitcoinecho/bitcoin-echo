<feature>
  <name>Chain Reorganization Test Suite</name>
  <files>test/unit/test_reorg.c, Makefile, test/run_all_tests.sh</files>
  <behavior>
    Test scenarios using the chainstate_t API directly (no chaser layer, pure consensus):

    1. Simple 2-block fork reorg:
       - Build chain A: genesis -> A1 -> A2 -> A3 (3 blocks)
       - Build chain B from A1: A1 -> B2 -> B3 -> B4 (3 blocks, more work than A)
       - Execute chain_reorganize from A3 tip to B4 tip
       - Assert: UTXOs created by A2, A3 are removed from UTXO set
       - Assert: UTXOs created by B2, B3, B4 are present in UTXO set
       - Assert: UTXOs from A1 and genesis remain (common ancestor)
       - Assert: chainwork at tip equals B4's accumulated work
       - Assert: chainstate_get_block_at_height(2) returns B2 hash, not A2

    2. Deep 6-block reorg:
       - Build chain A: genesis -> 6 blocks
       - Build chain B from genesis: genesis -> 7 blocks (more work)
       - Execute chain_reorganize
       - Assert: All chain A UTXOs gone, all chain B UTXOs present
       - Assert: chainwork reflects chain B

    3. Same-work competing chains (no reorg):
       - Build chain A: genesis -> A1 -> A2
       - Build chain B from genesis: genesis -> B1 -> B2 (same total work as A)
       - Assert: chainstate_should_reorg returns false (equal work = keep current)
       - Assert: No state change — original chain A UTXOs still present

    Synthetic block construction:
    - Each block needs: a valid-looking header with prev_hash, bits, and at least a coinbase tx
    - The coinbase tx must create at least one UTXO (output) that can be checked post-reorg
    - Use different bits values to control work: lower bits = more work = winning chain
    - Use the get_block_txs callback to provide transaction data during reorg

    The test does NOT need real PoW, real signatures, or real script validation.
    It tests the chainstate UTXO management and chainwork tracking during reorg.
  </behavior>
